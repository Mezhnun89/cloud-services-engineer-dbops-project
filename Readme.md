## Миграции

| Файл | Изменение |
| --- | --- |
| `V001__create_tables.sql` | Пять исходных таблиц |
| `V002__change_schema.sql` | Три таблицы `product`, `orders`, `order_product`; PK и FK; цена у товара, дата у заказа |
| `V003__insert_data.sql` | 6 товаров и по 10 миллионов заказов и позиций; настройка identity-последовательностей |
| `V004__create_index.sql` | Три индекса и обновление статистики |

V002 предназначена для пустой исходной схемы и отказывается удалять заполненные таблицы. Исходный `insert-data.sh` предназначен для отдельной демонстрационной БД `store_default`: не запускайте его в итоговой `store`, поскольку он удаляет таблицы.

V003 снимает два FK перед массовой загрузкой и возвращает их с полной валидацией в той же транзакции Flyway. Это позволяет избежать накопления миллионов событий FK-триггеров на ВМ с 2 ГБ памяти. При ошибке откатываются и данные, и изменения ограничений. [Документация PostgreSQL о массовой загрузке](https://www.postgresql.org/docs/16/populate.html).

Тип цены `double precision` сохранён по условиям курса. Для денежных расчётов в производственной системе стоит отдельно определить точное представление цены. Уже применённые миграции не редактируются.

## База и права доступа

Среда фактического запуска: Ubuntu 24.04.1, около 2 ГБ RAM, Docker 29.8.0, Compose 5.5.1, PostgreSQL 16.15, Flyway 10.20.1. Контейнер `dbops-postgres` ограничен 1 ГБ памяти и опубликован на `127.0.0.1:5432`. Параметры: `shared_buffers=128MB`, `work_mem=4MB`, `maintenance_work_mem=64MB`, `max_connections=30`, `max_parallel_workers_per_gather=0`. Flyway запускался с лимитом контейнера 512 МБ и Java heap 256 МБ.

На ВМ пароль создан автоматически и передан в psql через переменную окружения. Эквивалент выполненной подготовки для новой БД, от имени администратора PostgreSQL:

```sql
CREATE ROLE store_migrator LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password store_migrator
CREATE DATABASE store OWNER store_migrator;
REVOKE CONNECT ON DATABASE store FROM PUBLIC;
GRANT CONNECT ON DATABASE store TO store_migrator;
\connect store
GRANT USAGE, CREATE ON SCHEMA public TO store_migrator;
```

`\password` позволяет ввести собственный пароль без сохранения его в SQL-файле. Миграции выполняются от имени `store_migrator`, поэтому эта роль владеет созданными таблицами и может менять их структуру. Дополнительные права SUPERUSER, CREATEDB и CREATEROLE не выдавались.

Рабочий Compose и файлы паролей находятся вне репозитория, в `~/dbops-runtime`. Исходный `docker-compose.yml` в этом репозитории — шаблон курса для `store_default`, а не конфигурация фактически запущенной `store`.

## GitHub Actions

Workflow применяет Flyway перед двумя исходными шагами загрузки и запуска штатных автотестов. Эти два шага сохранены без изменений. Запуски миграций выполняются последовательно; `flyway clean` отключён.

Так как PostgreSQL слушает только localhost ВМ, подготовлен SSH-туннель: порт `15432` GitHub runner перенаправляется на `127.0.0.1:5432` ВМ. Flyway использует сеть runner через `--network=host`, а тестовый бинарный файл запускается непосредственно на runner. Ключ сервера проверяется строго; после работы туннель закрывается, временные файлы ключей удаляются. Этот путь пока подготовлен, но не проверен реальным запуском Actions.

В Settings → Secrets and variables → Actions нужно настроить Repository secrets:

| Secret | Значение |
| --- | --- |
| `DB_HOST` | `127.0.0.1` |
| `DB_PORT` | `15432` |
| `DB_NAME` | `store` |
| `DB_USER` | `store_migrator` |
| `DB_PASSWORD` | Пароль роли из защищённого файла на ВМ |
| `SSH_HOST` | Внешний адрес учебной ВМ |
| `SSH_PRIVATE_KEY` | Приватный ключ для разрешённого SSH-доступа пользователя `user` |
| `SSH_KNOWN_HOSTS` | Проверенная запись ключа SSH-сервера для адреса ВМ |

Значения паролей и приватных ключей хранятся в Actions Secrets, а не в файлах публичного репозитория. Запись known_hosts должна быть получена после сверки отпечатка сервера. [GitHub: использование Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

Push в `main` по умолчанию применяет миграции до версии 4. Для нового стенда можно установить repository variable `FLYWAY_TARGET=1` или `3`, чтобы выполнить промежуточную проверку и замер до индексов. Ручной запуск `workflow_dispatch` позволяет выбрать target и имеет приоритет над этой переменной. При target 1 или 3 весь набор автотестов может завершиться ошибкой, поскольку поздние этапы ещё не выполнены. Уменьшение target не откатывает миграции.

## Запрос за предыдущую неделю

Предыдущая неделя — завершённая календарная неделя с понедельника включительно до текущего понедельника исключительно. Запрос суммирует количество сосисок в позициях всех заказов; дополнительный фильтр статуса не задан в условии.

```sql
SELECT o.date_created AS order_date,
       SUM(op.quantity) AS sausages_quantity
FROM public.orders o
JOIN public.order_product op ON op.order_id = o.id
WHERE o.date_created >= date_trunc('week', CURRENT_DATE)::date - 7
  AND o.date_created < date_trunc('week', CURRENT_DATE)::date
GROUP BY o.date_created
ORDER BY o.date_created;
```

Используется `SUM(quantity)`, а не количество строк: одна позиция может содержать несколько сосисок. Дни без заказов отсутствуют в результате. Запрос сохранён в `sql/weekly_sales.sql`, замер с `\timing` и `EXPLAIN (ANALYZE, BUFFERS)` — в `sql/benchmark.sql`.

## Сравнение до и после индексов

На ВМ для обоих замеров вместо CURRENT_DATE зафиксирована дата `2026-09-06`. Интервал отчёта — с 24 по 30 августа 2026 включительно. Между измерениями применена V004; данные не перегенерировались. CSV с недельными суммами совпали.

| Измерение на полном объёме | До V004 | После V004 |
| --- | ---: | ---: |
| Отдельный SELECT, psql timing | 71 722.071 мс | 64 875.132 мс |
| Execution Time, EXPLAIN ANALYZE | 50 732.755 мс | 80 486.756 мс |
| Полное время EXPLAIN, psql timing | 50 757.785 мс | 80 575.936 мс |
| Доступ к orders | Seq Scan | Index Only Scan |
| Доступ к order_product | Seq Scan | Seq Scan |
| Строк после соединения | 777 617 | 777 617 |

Созданы `orders_date_created_id_idx(date_created, id)`, `order_product_order_id_idx(order_id) INCLUDE (quantity)` и `order_product_product_id_idx(product_id)`.

После V004 план использует индекс даты заказа. Однако Index Only Scan выполнил 216 027 обращений к таблице (Heap Fetches), а соединение сохранило полный просмотр 10 миллионов позиций. Hash Join использовал 8 batches; временный ввод-вывод — по 41 439 блоков чтения и записи в обоих планах. Индекс не устранил эти расходы. Возможность обходиться без чтения таблицы зависит также от карты видимости PostgreSQL. [Документация об Index Only Scan](https://www.postgresql.org/docs/16/indexes-index-only-scans.html).

Один обычный SELECT стал примерно на 9.5% быстрее, но выполнение под EXPLAIN оказалось примерно на 58.6% медленнее. **Устойчивое ускорение этими одиночными замерами не доказано.** Причины изменения времени без дополнительных измерений не установлены. Для дальнейшего исследования можно выполнить VACUUM (ANALYZE), затем серию сопоставимых прогретых запусков; такие действия в подтверждённый результат не включены.
